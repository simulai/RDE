## 六问六答（对应任务书 Task 5 原问题）

### 1. 当前 RDE 内核是否可靠地满足其设计承诺？

**分层回答——在可验证范围内可靠，在设计未裁决范围外不可宣称。**

- **可靠（有独立反例证据）**：任务书十条验收标准经 13 项对抗探针 + 68 项对抗测试攻击后**全部成立**：
  篡改/调序/删事件/哈希合法的非法注入全被检出；版本回溯与分叉隔离成立；真独立路线双向判定成立；
  冲突证据必经 `invalidated` 中转；报告如实输出 unjudgeable。对应一致性表"已实现且测试覆盖" **26 条**。
- **此前被高估**：Phase 1 交付时 12 项实现与文档冲突潜伏在绿灯下（最典型：既有测试曾**断言**义务
  `open` 的 Claim 可 `completed`，违反 L3）。11 项本轮已修复并披露，1 项（L1 路线存在性子条件）开放。
- **不可宣称**：3 项开放设计问题未裁决（答 3）+ 6 项仅文档设计未实现（答 2）→
  "设计承诺整体可靠成立"这句话**当前不成立**，只能说到"已实现且被独立验证的部分可靠"。

### 2. 哪些部分只是工程实现，哪些部分有独立验证？

| 层 | 内容 | 判据 |
|---|---|---|
| **有独立验证**（本轮新增，攻击者视角） | 哈希链+重放双层完整性（含攻击者重算哈希的注入）、版本回溯/分叉隔离、路线聚合与 unjudgeable、冲突不覆盖、权限闸门（北极星三闸门、agent 语义升级拒绝、L3）、schema↔实现一致（多节点 Δ、sufficiency、ID 规则）、干净环境 CI 双绿 | 反例测试与探针**独立于原测试**编写，首轮 15 项失败即证明其区分度 |
| **工程实现（自证，独立性弱）** | 三维转换表本身、`propagate` 的 BFS 完整性、决策/分支/重开 API 的内部逻辑 | 测试由开发者（我）编写，证明"符合我所写的测试"；算法内部正确性未经第三方形式化验证 |
| **仅文档（无实现）** | L2 版本确定检查、假设升级规则、反例自动落盘、schema 演进（Q-ARCH-001）、多 Agent、因果边 | 见一致性表"仅文档设计" 6 条 |

诚实边界：本轮把一批"工程自证"升级成了"有独立反例验证"，但**测试的作者仍是被审计者**——
这正是你计划中"第二轮独立理论审查"要补的位置。

### 3. 哪些设计存在语义漏洞？

**未修复（设计层，需裁决）：**
1. **Q-007 隐藏前提**：路线独立性 = 按声明的前提集，未声明的隐藏前提不可检测——
   完全未声明 → 命题在影响报告中**不可见**；声明一半 → `still_valid` **假阳性**
   （`test_c02a/c02b` 固化）。报告"未列出"≠"无影响"。
2. **R-017 版本钉住**：premise 按 ID 解析到**当前**版本，路线无法表达"我绑定 v1"；
   `claim.definition_versions` 与路线解析结果漂移（`test_b03/c03` 固化）。
   缓解：修订当刻的影响报告会标记需复核；修订之后无法重建当次判定。
3. **L1 边界张力**：文档要求真值前置"存在 completed 推导路线"（未实现，`test_e09` 固化），
   且若严格执行会与 refute 反例离场路径（原则 5）冲突——true/false 是否同规则需裁决。
4. **L2 未实现**：proposed→formalized 的"定义版本已确定"检查缺失（`test_e10` 固化）。
5. 低危观察：多节点报告 kind 折叠为 modified（F-G02）、循环静默终止无警告（F-F01）、
   内容重复边允许（F-F02）、裸 `replay()` 无链校验（F-A01，用法约束）。

**已修复的实现层语义漏洞（曾与设计冲突，留档不删）**：agent 可授予真值状态（F-E01）、
创建入口绕过 L1 绑定（F-E02）、L3 未实现（F-E03）、撤销路线不判失效（F-C01）、
失败创建毒化日志（F-A03）、撤回通路不可达（F-D01）等 11 项。

### 4. 哪些机制需要重新设计？

| 档 | 机制 | 为什么是"重设计"而非补丁 |
|---|---|---|
| 需要**新机制** | ① 路线版本绑定（`bound_versions` 或等价） | 涉及依赖传播语义变更，影响所有路线判定——不可局部打补丁 |
| | ② 隐藏前提检测（前提完备性审计） | 代码无法"检测不存在的声明"；需要元数据勾稽流程或导入期强制，属机制级新增 |
| | ③ `_emit` 事务化（先试应用、成功再提交） | 当前"先写后应用"靠 7 处前置检查兜底；新增 handler 若再引入 apply 抛错会回归——结构性问题 |
| 需要**文档级精确化** | ④ L1 的 true/false 分界；⑤ L2 的"版本已确定"判据 | 实现缺的是判据定义，不是代码量 |
| **无需重设计**（审计后站得住） | 三维状态分离、哈希链+重放双层、影响报告结构、分叉/版本机制 | 对抗攻击未击穿其核心语义 |
